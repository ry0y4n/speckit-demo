# プロジェクト憲法

## 基本原則

### I. コード品質

すべてのコードは以下の品質基準を満たさなければならない（MUST）。

- **可読性**: コードは自己文書化されていなければならない。
  変数名・関数名は意図を明確に伝える命名とし、略語の使用は
  広く認知されたもの（例: `id`, `url`, `config`）に限定する。
- **一貫性**: プロジェクト全体で統一されたコーディングスタイルを
  適用しなければならない。リンター・フォーマッターを CI で
  自動実行し、スタイル違反があるコードはマージしてはならない。
- **単一責任**: 各モジュール・関数・クラスは単一の責務のみを
  持たなければならない。1 つの関数が複数の責務を担う場合、
  分割を検討しなければならない。
- **技術的負債の管理**: 意図的な技術的負債は `TODO(<理由>)` で
  明示し、対応するイシューを作成しなければならない。暗黙的な
  技術的負債の蓄積は許容しない。
- **コードレビュー**: すべての変更はプルリクエストを通じて
  少なくとも 1 名のレビューを受けなければならない。レビューでは
  本原則への準拠を確認する。

**根拠**: 高い可読性と一貫性を維持することで、チームメンバーの
合流・離脱に耐えうる持続可能なコードベースを実現する。

### II. テスト標準

テストは品質保証の基盤であり、以下の基準を遵守しなければ
ならない（MUST）。

- **テストカバレッジ**: 新規コードのユニットテストカバレッジは
  80% 以上を維持しなければならない。重要なビジネスロジックは
  100% のカバレッジを目指す。
- **テストの独立性**: 各テストケースは他のテストに依存せず、
  任意の順序で実行可能でなければならない。共有状態の使用は
  禁止する。
- **テストの種類と責務**:
  - **ユニットテスト**: 個々の関数・メソッドの正確性を検証する。
    外部依存はモック・スタブで置換する。
  - **結合テスト**: コンポーネント間のインタラクションを検証する。
    API 契約・データフロー・エラー伝播を対象とする。
  - **E2E テスト**: ユーザーシナリオ全体の動作を検証する。
    主要なユーザージャーニーごとに最低 1 件を作成する。
- **CI 統合**: すべてのテストは CI パイプラインで自動実行
  しなければならない。テスト失敗時はマージをブロックする。
- **テストの命名**: テスト名は「何を」「どの条件で」「どうなるか」を
  明確に表現しなければならない
  （例: `test_ユーザー作成_メール重複時_エラーを返す`）。

**根拠**: 包括的かつ独立したテストにより、リファクタリングや
機能追加時のリグレッションを早期に検出し、デリバリー速度と
品質を両立する。

### III. ユーザー体験の一貫性

ユーザー向けのすべてのインターフェースは統一された体験を
提供しなければならない（MUST）。

- **デザインシステム**: 共通のデザインシステム（カラーパレット、
  タイポグラフィ、スペーシング、コンポーネントライブラリ）を
  定義し、すべての UI 実装はこれに準拠しなければならない。
- **インタラクションパターン**: ナビゲーション、フォーム送信、
  エラー表示、ローディング状態などのインタラクションパターンは
  プロジェクト全体で統一しなければならない。
- **エラーハンドリング**: ユーザー向けエラーメッセージは
  以下の要件を満たさなければならない:
  - 何が起きたか明確に伝える
  - 次に何をすべきか提示する
  - 技術的詳細をユーザーに露出しない
- **アクセシビリティ**: WCAG 2.1 AA 基準への準拠を
  目標としなければならない。キーボード操作・スクリーンリーダー
  対応・適切なコントラスト比を確保する。
- **レスポンシブ対応**: サポート対象のすべてのデバイス・
  画面サイズで適切に表示・動作しなければならない。

**根拠**: 一貫した UI/UX はユーザーの学習コストを低減し、
信頼感を醸成する。断片的な体験はユーザー離脱を招く。

### IV. パフォーマンス要件

システムは以下のパフォーマンス基準を満たさなければならない
（MUST）。遵守状況は継続的に計測・監視する。

- **レスポンスタイム**:
  - API レスポンスの p95 は 200ms 以内でなければならない
  - ページ初期表示（LCP）は 2.5 秒以内でなければならない
  - ユーザー操作への応答（INP）は 200ms 以内でなければならない
- **リソース効率**:
  - メモリリークを発生させてはならない
  - CPU 使用率はアイドル時 5% 以下でなければならない
  - バンドルサイズの増加は各 PR で定量的に正当化しなければならない
- **スケーラビリティ**:
  - 想定ピーク負荷の 2 倍で正常動作することを検証しなければならない
  - データ量の増加に対して線形以下の性能劣化に留めなければならない
- **監視と計測**:
  - パフォーマンスメトリクスを本番環境で継続的に収集しなければならない
  - 閾値超過時にアラートを発報する仕組みを構築しなければならない
  - パフォーマンスリグレッションを CI で検出する仕組みを
    導入しなければならない

**根拠**: パフォーマンスはユーザー体験の根幹であり、事後対応
ではなく設計段階から組み込むことで、大規模なリワークを防ぐ。

## 技術的意思決定の指針

技術選択・設計判断を行う際は、以下のフレームワークに従わなけ
ればならない。

- **原則との整合性**: すべての技術的意思決定は上記 4 原則との
  整合性を文書化しなければならない。原則に反する決定は、
  明確な根拠・期限付きの例外申請・是正計画を伴う場合に限り
  許容する。
- **ADR（Architecture Decision Record）**: 重要な技術的決定は
  ADR として記録しなければならない。ADR には背景・選択肢・
  決定理由・トレードオフを含める。
- **依存関係の選定基準**:
  - メンテナンス状況（直近 6 ヶ月以内の更新があること）
  - ライセンスの互換性
  - セキュリティ脆弱性の履歴
  - コミュニティの規模と活発さ
- **シンプルさの優先**: 複数の選択肢がある場合、最もシンプルな
  解決策を選択しなければならない（YAGNI 原則）。複雑性の
  導入には定量的な正当化を求める。

## 実装選択の基準

実装レベルの判断は以下の基準に照らして行わなければならない。

- **既存パターンの再利用**: プロジェクト内に確立されたパターンが
  ある場合、新規パターンの導入よりも既存パターンの再利用を
  優先しなければならない。
- **段階的な改善**: 大規模なリファクタリングよりも、段階的な
  改善を優先しなければならない。各ステップは独立してテスト・
  デプロイ可能でなければならない。
- **後方互換性**: パブリック API の破壊的変更は非推奨（deprecation）
  期間を設けたうえで段階的に実施しなければならない。
- **設定よりも規約**: 明示的な設定よりも合理的なデフォルト値と
  規約を優先し、設定の複雑さを最小化する。

## ガバナンス

本憲法はプロジェクトにおけるすべての技術的実践の最上位規範で
ある。具体的な運用手順・ガイダンスよりも本憲法が優先する。

### 改正手続き

1. 改正提案はプルリクエストとして提出しなければならない。
2. 改正内容の影響範囲を明示し、既存コード・プロセスへの
   影響を評価しなければならない。
3. チームメンバーの過半数の承認を得なければならない。
4. 改正時にはバージョンをセマンティックバージョニング規則に
   従って更新する:
   - **MAJOR**: 原則の削除・再定義など後方互換性のない変更
   - **MINOR**: 新原則の追加・既存セクションの大幅な拡張
   - **PATCH**: 文言の明確化・誤字修正・非意味的な改善

### 準拠確認

- すべてのプルリクエストのレビューにおいて、本憲法への
  準拠を確認しなければならない。
- 四半期ごとに憲法準拠の総合レビューを実施しなければならない。
- plan テンプレートの「Constitution Check」セクションを活用し、
  各機能の設計段階で原則との整合性を検証する。

### 例外の管理

- 原則からの逸脱は、明確な根拠・影響範囲・是正期限を
  文書化したうえで例外申請を行わなければならない。
- 例外は四半期レビュー時に再評価し、継続の可否を判断する。
